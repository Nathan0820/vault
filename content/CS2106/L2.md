# 📘 L2: Process Abstraction

> [!abstract] Lecture Goal
> Understand why the OS needs the process abstraction, master the three contexts (Memory, Hardware, OS), and know how processes transition through states and interact with the OS via system calls, exceptions, and interrupts.

> [!tip] The Big Picture
> A process is the OS's fundamental unit of execution. Everything the OS does — scheduling, memory management, IPC — revolves around processes. Understanding this abstraction is foundational.

---

## 1. Why We Need Processes

### 🧠 Core Concept

A **program** is a static set of instructions sitting on disk. A **process** (also called a _task_ or _job_) is a **dynamic abstraction** of a program _currently executing_ on the CPU.

The OS must support **multiprogramming** — running multiple programs seemingly at the same time by rapidly switching between them. To switch from running Program A to Program B, the OS needs to:

1. **Save** all the execution information of Program A
2. **Load** the execution information of Program B

This requires a formal structure to describe a running program → **the Process**.

| Context | Contents |
| :--- | :--- |
| **Memory Context** | Code (Text), Data, Stack, Heap |
| **Hardware Context** | Registers, PC, Stack Pointer, Frame Pointer |
| **OS Context** | Process ID, Process State, Resources used |

```mermaid
flowchart TD
    Program["Program<br/>(Static, on disk)"]
    Process["Process<br/>(Dynamic, executing)"]
    
    Program -->|"Loaded into memory"| Process
    
    Process --> MC["Memory Context<br/>Text, Data, Stack, Heap"]
    Process --> HC["Hardware Context<br/>PC, SP, FP, Registers"]
    Process --> OC["OS Context<br/>PID, State, Resources"]
    
    style Program fill:#ffcc99
    style Process fill:#99ff99
```

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: Program ≠ Process
> A program is **passive** (a file on disk). A process is **active** (it has memory allocated, a PC pointing somewhere, registers with values). The same program can spawn multiple processes simultaneously (e.g., two terminal windows running the same shell).

---

### ❓ Mock Exam Questions

> [!question] Q1: Dynamic Abstraction

> <details><summary>Answer</summary>
>
> **Answer:**
> A process captures the runtime state of a program — its memory allocations, register values, and execution position. Unlike a static program file, a process changes continuously as it executes. The abstraction lets the OS manage execution without knowing program internals.
> </details>

> [!question] Q2: Three Contexts

> <details><summary>Answer</summary>

> - **Hardware Context**: Program Counter, Stack Pointer, General Purpose Registers
> - **OS Context**: Process ID (PID), Process State, Open file descriptors
> </details>

## 2. Memory Context

### 2.1 Code & Data Regions

#### 🧠 Core Concept

When a program is loaded into memory, it is divided into regions:

| Region | Description | Properties |
| :--- | :--- | :--- |
| **Text Segment** | Machine instructions (compiled code) | Read-only during execution |
| **Data Segment** | Global and static variables | Size known at compile time |

**Example:** The C code `int i = 0; i = i + 20;` compiles to:

```asm
addi $1, $0, 0      # register $1 = 0
sw   $1, 4096       # i = 0 (store to address 4096 in Data)
lw   $2, 4096       # load i
addi $3, $2, 20     # $3 = i + 20
sw   $3, 4096       # i = i + 20
```

The assembly instructions live in **Text**; variable `i` lives in **Data** at address 4096.

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: Local variables ≠ Data segment
> The Data region is only for **global/static** variables known at compile time. Local variables live on the **stack**.

---

### 2.2 Stack Memory & Function Calls

#### 🧠 Core Concept

Functions require memory that is _created when called_ and _destroyed when they return_. This is too dynamic for the Data region.

**Solution: Stack Memory**

Each function invocation gets a **stack frame** (activation record) pushed onto the stack. The stack follows **LIFO** order — most recently called function is at the top.

| Field | Purpose |
| :--- | :--- |
| **Return PC** | Where to resume execution in the caller |
| **Parameters** | Arguments passed to the function |
| **Saved SP** | Old Stack Pointer to restore on return |
| **Saved FP** | Old Frame Pointer |
| **Saved Registers** | Registers the callee must preserve |
| **Local Variables** | Space for variables inside the function |
| **Return Result** | Return value before returning |

```mermaid
flowchart TD
    subgraph Stack ["Stack Memory"]
        direction TB
        FrameH["Stack Frame for h()<br/>├─ Local vars<br/>├─ Saved regs<br/>├─ Parameters<br/>└─ Return PC"]
        FrameG["Stack Frame for g()"]
        FrameF["Stack Frame for f()"]
        FrameMain["Stack Frame for main()"]
    end
    
    SP["SP → Top of stack"]
    
    style Stack fill:#ffcc99
    style FrameH fill:#99ff99
```

**Key Registers:**

| Register | Role |
| :--- | :--- |
| **Stack Pointer (SP)** | Points to the top of the stack; moves dynamically |
| **Frame Pointer (FP)** | Fixed reference within current frame; stable for accessing locals/parameters |

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: SP vs FP confusion
> **SP** = moves dynamically, always points to current stack top. **FP** = stays fixed for one function call, used as stable reference.

> [!danger] Pitfall: No universal calling convention
> The exact stack frame layout varies by architecture and language. The key concepts (return address, parameters, locals) are universal; their ordering and who sets them up differs.

> [!danger] Pitfall: Stack overflow
> Unbounded recursion causes the stack to grow until it collides with the heap → crash.

---

### ❓ Mock Exam Questions

> [!question] Q3: Return PC Purpose
> What is the purpose of saving the Return PC on the stack frame? What would go wrong if we did not save it?
> <details><summary>Answer</summary>
>
> **Answer:**
> The Return PC tells the CPU where to resume execution in the caller after the callee returns. Without it, the callee wouldn't know where to return — execution would jump to an arbitrary location, likely crashing.
> </details>

> [!question] Q4: Register Spilling
> What is "register spilling" and why is it needed?
> <details><summary>Answer</summary>
>
> **Answer:**
> CPUs have limited General Purpose Registers (GPRs). When a function needs more registers than available, it "spills" some register values to memory (in its stack frame), uses the registers freely, then restores them before returning.
> </details>

---

### 2.3 Heap Memory

#### 🧠 Core Concept

Some memory needs can only be determined **at runtime** (e.g., allocating an array whose size comes from user input). This can't go in Data or Stack:

1. **Not Data** → Size unknown at compile time
2. **Not Stack** → No fixed deallocation time

**Solution: Heap Memory**

```
Memory Layout of a Process:
┌──────────────┐  High Address
│    Stack     │  (grows downward ↓)
│      ↓       │
│   (free)     │
│      ↑       │
│    Heap      │  (grows upward ↑)
├──────────────┤
│    Data      │  (global variables)
├──────────────┤
│    Text      │  (instructions)
└──────────────┘  Low Address
```

| Region | Allocation | Deallocation |
| :--- | :--- | :--- |
| **Stack** | Automatic (function call) | Automatic (function return) |
| **Heap** | Explicit (`malloc()`) or implicit (GC) | Explicit (`free()`) or GC |

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: Using stack for large dynamic data
> Variable-Length Arrays (VLAs) on the stack are risky for large sizes — can cause stack overflow. Use `malloc()` for large/dynamic allocations.

> [!danger] Pitfall: Memory leaks
> In C/C++, failing to `free()` heap memory means it's never reclaimed until process termination.

---

### ❓ Mock Exam Questions

> [!question] Q5: Heap vs Stack
> Why can dynamically allocated memory (`malloc()`) not be placed in the Stack region?
> <details><summary>Answer</summary>
>
> **Answer:**
> Stack memory follows strict LIFO allocation — a function's local data is freed when it returns. Heap data must persist beyond function boundaries (e.g., a function returns a pointer to allocated memory). Placing it on the stack would cause it to be freed prematurely.
> </details>

> [!question] Q6: Heap Fragmentation
> What is heap fragmentation? Give a scenario that causes it.
> <details><summary>Answer</summary>
>
> **Answer:**
> Fragmentation occurs when free memory is scattered into small non-contiguous blocks. Example: Allocate 100 bytes, then 50 bytes. Free the 100-byte block. Now you have a 100-byte gap, but if you need 80 bytes and a separate 50-byte block exists elsewhere, the 100-byte gap might be unusable if allocation requires contiguous space.
> </details>

## 3. Hardware Context

### 🧠 Core Concept

The hardware context captures the state of CPU registers. During a **context switch**, the OS must save the current hardware context (into the PCB) and restore the new process's hardware context.

| Register | Role |
| :--- | :--- |
| **General Purpose Registers** | Intermediate values, function arguments, return values |
| **Program Counter (PC)** | Address of next instruction to execute |
| **Stack Pointer (SP)** | Top of stack |
| **Frame Pointer (FP)** | Fixed reference in current stack frame |

```mermaid
flowchart LR
    subgraph ContextSwitch ["Context Switch"]
        Save["Save current process<br/>PC, SP, FP, GPRs → PCB"]
        Restore["Load next process<br/>PC, SP, FP, GPRs ← PCB"]
    end
    
    Save --> Restore
    
    style Save fill:#ffcc99
    style Restore fill:#99ff99
```

The **Program Counter** is critical: without saving/restoring it, the OS cannot resume a process at the correct instruction.

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: Non-atomic context save
> The hardware context must be saved **atomically**. If the OS saves some registers but gets interrupted mid-save, the stored context will be inconsistent. Real systems disable interrupts during save/restore.

## 4. OS Context – Process State & ID

### 🧠 Core Concept

#### Process ID (PID)

Every process gets a unique numeric identifier — the **Process ID (PID)**. This lets the OS distinguish processes.

#### The 5-State Process Model

```mermaid
flowchart LR
    New["New"]
    Ready["Ready"]
    Running["Running"]
    Blocked["Blocked"]
    Terminated["Terminated"]
    
    New -->|"admit"| Ready
    Ready -->|"schedule"| Running
    Running -->|"release CPU"| Ready
    Running -->|"event wait"| Blocked
    Blocked -->|"event occurs"| Ready
    Running -->|"exit"| Terminated
    
    style New fill:#e0e0e0
    style Ready fill:#99ff99
    style Running fill:#ffcc99
    style Blocked fill:#ff9999
    style Terminated fill:#cccccc
```

| State | Meaning |
| :--- | :--- |
| **New** | Process just created; still initializing |
| **Ready** | Process is ready to run but waiting for CPU |
| **Running** | Process is currently executing on the CPU |
| **Blocked** | Process is waiting for an event (I/O, etc.) |
| **Terminated** | Process has finished; OS may need cleanup |

**Key Transitions:**

| Transition | Trigger |
| :--- | :--- |
| New → Ready | Initialization complete, admitted by OS |
| Ready → Running | Scheduler selects this process |
| Running → Ready | Preempted by scheduler OR voluntarily yields |
| Running → Blocked | Requests unavailable resource (I/O wait) |
| Blocked → Ready | Awaited event occurs |
| Running → Terminated | Process calls `exit()` or crashes |

> [!warning] Global Constraint
> With $m$ CPUs, **at most $m$ processes** can be Running simultaneously. Multiple processes can be Ready or Blocked at the same time.

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: Ready ≠ Blocked
> A **Ready** process has everything it needs to run — just waiting for a CPU slot. A **Blocked** process cannot run even if a CPU is free — it's waiting for an external event.

> [!danger] Pitfall: Running → Ready vs Running → Blocked
> - **Running → Ready**: process _could_ run, just lost its CPU time slot
> - **Running → Blocked**: process _cannot_ run until something happens externally

---

### ❓ Mock Exam Questions

> [!question] Q7: Ready vs Blocked
> Describe the difference between Ready and Blocked states. Give a concrete example of a transition from Running → Blocked and then Blocked → Ready.
> <details><summary>Answer</summary>
>
> **Answer:**
> - **Ready**: Process can run immediately if given CPU; waiting only for scheduler.
> - **Blocked**: Process cannot run; waiting for external event (I/O, signal).
>
> **Example:** Process calls `read()` from disk → Running → Blocked. When disk completes, interrupt handler moves it → Blocked → Ready.
> </details>

> [!question] Q8: Maximum States
> On a single-CPU system with 10 processes, what is the maximum number in Running, Ready, and Blocked states?
> <details><summary>Answer</summary>
>
> **Answer:**
> - **Running**: at most **1** (only one CPU)
> - **Ready**: at most **9** (if 1 is Running, others could all be Ready)
> - **Blocked**: at most **10** (all could be waiting for I/O)
> </details>

> [!question] Q9: State Transition Trace
> A process calls `read()` to read from disk. Trace the state transitions using the 5-state model until it resumes executing.
> <details><summary>Answer</summary>
>
> **Answer:**
> 1. Process is **Running**, calls `read()`
> 2. **Running → Blocked** (waiting for disk I/O)
> 3. Disk I/O completes, interrupt fires
> 4. **Blocked → Ready** (event occurred)
> 5. Scheduler picks this process
> 6. **Ready → Running** (resumes execution)
> </details>

## 5. Process Control Block & Process Table

### 🧠 Core Concept

The **Process Control Block (PCB)** is the kernel's data structure storing all information about one process:

```
┌─────────────────────────────┐
│  Process Control Block      │
├─────────────────────────────┤
│  PID                        │  ← OS Context
│  Process State              │
│  Resources Used             │
├─────────────────────────────┤
│  PC, SP, FP, …              │  ← Hardware Context
│  General Purpose Registers  │
├─────────────────────────────┤
│  Memory Region Info         │  ← Memory Context
│  (pointers to regions)      │
└─────────────────────────────┘
```

The **Process Table** is the collection of all PCBs — one entry per process.

**Context switch mechanism:**

1. Save current process's hardware context → its PCB
2. Load next process's hardware context ← its PCB
3. CPU now runs the new process

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: PCB stores metadata, not data
> The PCB stores _pointers/metadata_ about memory regions. The actual stack and heap data live in the process's own memory space, not inside the PCB.

## 6. OS Interaction with Processes

### 🧠 Core Concept

Processes interact with the OS in three ways:

| Type | Initiated By | Timing | Example |
| :--- | :--- | :--- | :--- |
| **System Call** | Process (voluntary) | Synchronous | `getpid()`, `read()` |
| **Exception** | Hardware (instruction error) | Synchronous | Division by zero, segfault |
| **Interrupt** | Hardware (external event) | Asynchronous | Timer, keyboard |

### 6.1 System Calls

A **system call** is how a user process requests OS kernel services. It requires a **mode switch** (user → kernel) via a **TRAP** instruction.

**Mechanism (7 steps):**

| OS | Number of System Calls |
| :--- | :--- |
| Unix/POSIX | ~100 |

### 6.2 Exceptions

An **exception** is triggered by instruction execution causing an error:

- **Arithmetic**: overflow, division by zero
- **Memory**: illegal address, misaligned access

**Effect:** CPU transfers control to an **exception handler**. After handling, execution may resume (or process terminates for fatal exceptions).

---

### 6.3 Interrupts

An **interrupt** is triggered by external hardware events, independent of program execution:

- Timer interrupt (preemption)
- I/O completion (disk read done)
- Network packet arrived

**Handler steps:**

1. Save register/CPU state
2. Perform handler routine
3. Restore register/CPU state
4. Return from interrupt

![[Screenshot 2026-04-20 at 1.11.46 PM.png]]

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: System call ≠ Function call
> A system call must switch privilege levels (user → kernel) via TRAP. Cost is much higher than a regular function call.

> [!danger] Pitfall: Synchronous vs Asynchronous
> - **Synchronous**: tied to a specific instruction (system call, exception)
> - **Asynchronous**: can happen at any time (interrupt)

## 7. Process Identification & Information

### 🧠 Core Concept

Every running program in Unix is represented as a **process** — a live execution instance with its own identity and state.

**Key identifiers stored per process:**

| Field | Description |
| :--- | :--- |
| **PID** | Process ID — a unique integer assigned to each process |
| **PPID** | Parent PID — the PID of the process that spawned this one |
| **State** | Current state: Running, Sleeping, Stopped, or Zombie |
| **CPU Time** | Cumulative time the process has used the CPU |

> [!tip] Inspecting Processes
> Use the `ps` command in your terminal to inspect running processes and see their PIDs, states, and parent relationships.

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: Confusing PID with PPID
> **PID** identifies *this* process; **PPID** identifies its *parent*. They serve different purposes — don't mix them up.

> [!danger] Pitfall: Zombie is a real, valid state
> "Zombie" sounds scary but is a legitimate process state. A zombie process has finished execution but hasn't had its resources fully cleaned up yet (because the parent hasn't called `wait()` yet).

> [!danger] Pitfall: `ps` shows a snapshot
> The `ps` command shows a **snapshot** in time — process states change rapidly! A process shown as "Running" might be "Sleeping" by the time you read the output.

---

### ❓ Mock Exam Questions

> [!question] Q1: PID Definition
> What does the acronym PID stand for, and what type of value is it?
> <details><summary>Answer</summary>
>
> **Answer:**
> PID stands for **Process ID**. It is a unique positive integer assigned by the OS to each process. PID 1 is typically the `init` process; PIDs are reused after a process terminates.
> </details>

> [!question] Q2: Process States
> Name the four process states that can appear in the `ps` output.
> <details><summary>Answer</summary>
>
> **Answer:**
> The four states are: **Running** (currently executing), **Sleeping** (waiting for I/O), **Stopped** (paused by signal), and **Zombie** (terminated but not yet reaped).
> </details>

> [!question] Q3: PPID and the Root Process
> What does PPID represent, and which process has no meaningful PPID?
> <details><summary>Answer</summary>
>
> **Answer:**
> **PPID** is the PID of the parent process that created this process. The `init` process (PID 1) has no parent — its PPID is typically 0 or itself, representing the root of the process tree.
> </details>

> [!question] Q4: Zombie Cleanup
> A student runs `ps` and sees a process listed as "Zombie". Explain what this means in terms of process lifecycle, and what needs to happen for it to be fully cleaned up.
> <details><summary>Answer</summary>
>
> **Answer:**
> A zombie process has terminated (called `exit()`) but its entry remains in the process table because the parent hasn't collected its exit status. To clean it up, the parent must call `wait()` (or `waitpid()`), which reads the exit status and removes the process entry. If the parent never calls `wait()`, the zombie persists until the parent terminates.
> </details>

## 8. Process Creation — `fork()`

### 🧠 Core Concept

`fork()` is the primary Unix system call for creating a new process.

```c
#include <unistd.h>
int fork();
```

When called, `fork()` creates a **child process** that is nearly an exact copy of the parent. Both processes continue executing from the line *after* `fork()`.

**Return values — this is the key to telling them apart:**

| Return Value | Meaning |
| :--- | :--- |
| **PID of child** | You are the parent process |
| **0** | You are the child process |
| **-1** | An error occurred |

**What the child inherits (copies) from the parent:**

- Same code (program text)
- Same address space
- Same open file descriptors
- Same CPU registers / execution context

**What differs between parent and child:**

- PID (each gets a unique one)
- PPID (child's PPID = parent's PID)
- The return value of `fork()` itself

---

### Code Examples

**Example 1 — Basic fork:**

```c
printf("I am ONE\n");
fork();
printf("I am seeing DOUBLE\n");
```

Output:

```
I am ONE
I am seeing DOUBLE
I am seeing DOUBLE
```

- `"I am ONE"` prints once — only the parent exists at that point.
- After `fork()`, **two** processes exist (parent + child), both continuing from the next line.
- So `"I am seeing DOUBLE"` prints **twice** — once per process.

**Example 2 — Distinguishing parent from child:**

```c
result = fork();
if (result != 0) {
    // This branch runs in the PARENT
    printf("P: My Id is %i\n", getpid());
    printf("P: Child Id is %i\n", result);
} else {
    // This branch runs in the CHILD
    printf("C: My Id is %i\n", getpid());
    printf("C: Parent Id is %i\n", getppid());
}
```

- Parent gets `result = child's PID` (non-zero) → enters the `if` branch.
- Child gets `result = 0` → enters the `else` branch.
- This is the standard pattern for giving parent and child different tasks.

**Example 3 — Independent memory spaces:**

```c
int var = 1234;
result = fork();
if (result != 0) { var++; }   // Parent: var becomes 1235
else             { var--; }   // Child:  var becomes 1233
```

There are **TWO `var` variables in memory** — one in the parent's memory space and one in the child's (a copy). Changes to one do not affect the other.

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: Both processes continue after fork()
> After `fork()`, **both parent AND child continue running**. This is a very common source of confusion. Think of it as a "fork in the road" — one process becomes two.

> [!danger] Pitfall: Child's data is a COPY
> The child's data is a **copy**, not a reference. Don't expect changes in the child to show up in the parent.

> [!danger] Pitfall: No guaranteed execution order
> The order of execution between parent and child is **not guaranteed**. The OS scheduler decides who runs first — you cannot assume the parent runs before the child.

> [!danger] Pitfall: Handle fork() failure
> Don't forget to handle `fork()` returning `-1` (failure case) in production code.

---

### ❓ Mock Exam Questions

> [!question] Q1: fork() Return Values
> What are the three possible return values of `fork()`, and what does each mean?
> <details><summary>Answer</summary>
>
> **Answer:**
> - **Child's PID (positive integer)**: Returned to the parent — identifies the newly created child.
> - **0**: Returned to the child — indicates you are the child process.
> - **-1**: Returned on error — fork failed (e.g., process limit reached).
> </details>

> [!question] Q2: Processes After fork()
> After `fork()` is called, how many processes are there, and where do they each resume execution?
> <details><summary>Answer</summary>
>
> **Answer:**
> There are **two processes** after `fork()` — the parent and the child. Both resume execution at the line **immediately after** the `fork()` call, with identical program counters.
> </details>

> [!question] Q3: Memory Isolation After fork()
> If a parent has variable `x = 10` before calling `fork()`, and the child sets `x = 99`, what is the value of `x` in the parent process?
> <details><summary>Answer</summary>
>
> **Answer:**
> The parent's `x` remains **10**. The child gets its own copy of `x`; modifying it does not affect the parent's copy. They are in separate address spaces.
> </details>

> [!question] Q4: Double Fork Output
> How many times will `"Hello"` be printed by the following program, and why?
> ```c
> int main() {
>     fork();
>     fork();
>     printf("Hello\n");
>     return 0;
> }
> ```
> <details><summary>Answer</summary>
>
> **Answer:**
> **4 times**. After the first `fork()`: 2 processes. After the second `fork()`: each of those 2 forks again → 4 processes total. All 4 execute `printf("Hello\n")`.
> </details>

## 9. Executing a New Program — `exec()` Family

### 🧠 Core Concept

`fork()` alone just duplicates the parent. To run a **completely different program** in the child, we use the `exec()` family of system calls.

The most straightforward variant is `execl()`:

```c
#include <unistd.h>
int execl(const char *path, const char *arg0, ..., const char *argN, NULL);
```

| Parameter | Meaning |
| :--- | :--- |
| **`path`** | Full path to the executable (e.g., `"/bin/ls"`) |
| **`arg0`** | Conventionally the program name itself |
| **`arg1...argN`** | Additional command-line arguments |
| **`NULL`** | Sentinel — marks the end of the argument list |

**Key behaviour:** `execl()` **replaces** the current process's code with the new program. The PID stays the same, but the program being run changes entirely. If `execl()` succeeds, **it never returns** — the old code is gone!

**Other `exec()` variants:** `execv`, `execle`, `execlp`, `execvp` — they differ in how arguments and environment variables are passed. Use `man execl` to explore them.

**The Power Combo: `fork()` + `exec()`**

This is the standard Unix idiom for running new programs:

1. Parent calls `fork()` → creates a child
2. Child calls `exec()` → child becomes a new program
3. Parent continues doing its own work (or waits)

---

### Code Examples

**`execl()` example:**

```c
int main() {
    execl("/bin/ls", "ls", "-l", NULL);
}
```

- `path = "/bin/ls"` — location of the `ls` program
- `arg0 = "ls"` — the program name (by convention, `argv[0]` is always the program name)
- `arg1 = "-l"` — flag to list in long format
- This is exactly equivalent to typing `ls -l` in your terminal.

**Command-line arguments in C:**

```c
int main(int argc, char* argv[]) { ... }
```

Running `a.out 123 hello world` gives:

- `argc = 4` (program name + 3 args)
- `argv[0] = "a.out"`, `argv[1] = "123"`, `argv[2] = "hello"`, `argv[3] = "world"`

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: execl() never returns on success
> `execl()` does **NOT** return on success. Any code written after `execl()` in the child only runs if `execl()` *fails*. Use this to detect errors!

> [!danger] Pitfall: Missing NULL sentinel
> **Always terminate the argument list with `NULL`**. Forgetting this causes undefined behaviour (a very nasty bug).

> [!danger] Pitfall: arg0 should be program name
> `arg0` should be the program name, not the path. By convention, `argv[0]` in the new program will be what you pass as `arg0`.

> [!danger] Pitfall: fork() alone is not enough
> `fork()` alone is **not enough** to run a different program — you need `exec()` too.

---

### ❓ Mock Exam Questions

> [!question] Q1: PID After exec()
> What happens to the process's PID when `execl()` is called successfully?
> <details><summary>Answer</summary>
>
> **Answer:**
> The PID **stays the same**. `execl()` replaces the program code, but does not create a new process. The process identity (PID, PPID, open file descriptors) is preserved.
> </details>

> <details><summary>Answer</summary>
>
> **Answer:**
> `NULL` is a **sentinel** that marks the end of the argument list. Since `execl()` takes a variable number of arguments, it needs a way to know when the argument list ends. Without `NULL`, it would read garbage memory.
> </details>

> [!question] Q3: Why fork() + exec()?
> Why is `fork()` alone insufficient for running a new, different program?
> <details><summary>Answer</summary>
>
> **Answer:**
> `fork()` only creates a copy of the parent process — the child runs the **same** program code. To run a **different** program, the child must call `exec()` to replace its code with the new program. `fork()` + `exec()` together enable process creation and program execution.
> </details>

> </details>

## 10. Process Termination — `exit()`

### 🧠 Core Concept

A process ends its execution by calling `exit()`:

```c
#include <stdlib.h>
void exit(int status);
```

The `status` value follows Unix convention:

| Status | Meaning |
| :--- | :--- |
| **0** | Normal / successful termination |
| **Non-zero** | Error / abnormal termination |

**What happens on exit:**

- **Most** resources are released: open file descriptors, memory, etc.
- **Some** info is retained: PID, exit status, CPU accounting — needed for the parent's `wait()` call
- The process enters **Zombie** state until the parent collects its exit status

**Implicit `exit()`:** Returning from `main()` automatically calls `exit()`. So most programs don't need to call it explicitly.

```c
int main() {
    printf("Goodbye!\n");
}  // exit() is called implicitly here
```

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: exit() never returns
> `exit()` does **not return** — the process is terminated. There is no coming back!

> [!danger] Pitfall: 0 means success
> Status code **`0` means success**, NOT failure. This is the opposite of what some students intuitively expect.

> [!danger] Pitfall: Zombie is normal
> Even after `exit()`, a process briefly becomes a **zombie** — this is normal and expected. It only becomes a *problem* if the parent never calls `wait()`.

> [!danger] Pitfall: Files are flushed automatically
> Open files are flushed automatically on `exit()` — you won't lose buffered output.

---

### ❓ Mock Exam Questions

> [!question] Q1: Exit Status 0
> What does an exit status of `0` conventionally mean in Unix?
> <details><summary>Answer</summary>
>
> **Answer:**
> Exit status `0` means **successful termination**. Non-zero values indicate an error or abnormal termination.
> </details>

> [!question] Q2: Resources Not Freed
> What resources are **NOT** immediately freed when a process calls `exit()`?
> <details><summary>Answer</summary>
>
> **Answer:**
> The process's **PID**, **exit status**, and **CPU accounting info** are retained in the process table. These are needed so the parent can call `wait()` and retrieve the child's exit status. They are only freed when the parent calls `wait()`.
> </details>

> [!question] Q3: Implicit exit()
> Does a program need to explicitly call `exit()` — why or why not?
> <details><summary>Answer</summary>
>
> **Answer:**
> No — returning from `main()` automatically calls `exit()` with the return value as the status. Most programs simply use `return 0;` from `main()`. Explicit `exit()` is only needed for early termination or when exiting from a function other than `main()`.
> </details>

> [!question] Q4: Exit Cleanup Sequence
> Explain the sequence of events from when a child process calls `exit(1)` to when its resources are fully cleaned up. What role does the parent play?
> <details><summary>Answer</summary>
>
> **Answer:**
> 1. Child calls `exit(1)` → most resources freed (memory, file descriptors).
> 2. Child enters **Zombie** state; PID and exit status retained.
> 3. OS sends `SIGCHLD` signal to parent.
> 4. Parent calls `wait()` → receives child's PID and exit status.
> 5. OS removes zombie entry from process table → fully cleaned up.
> </details>

## 11. Parent-Child Synchronization — `wait()`

### 🧠 Core Concept

`wait()` allows a parent to **block and wait** for a child to finish:

```c
#include <sys/types.h>
#include <sys/wait.h>
int wait(int *status);
```

**Behaviour:**

- Parent **blocks** (suspends) until at least one child terminates
- Returns the **PID** of the terminated child
- Writes the child's exit code into `*status`
- **Cleans up** the zombie child's remaining process table entry

Pass `NULL` if you don't care about the exit status:

```c
wait(NULL);
```

**Variants:**

| Call | Purpose |
| :--- | :--- |
| **`wait()`** | Wait for any child |
| **`waitpid(pid, ...)`** | Wait for a specific child by PID |
| **`waitid(...)`** | Wait for any child to *change* status |

---

### Process Lifecycle Diagram

```
exec/fork → [Parent Process] ─── wait() ──────────────────→ [Parent resumes]
                  │                                                ↑
                fork()                                    process entry
                  ↓                                       cleaned up
            [Child Process] → execl() → [Child runs] → exit() → [Zombie] ─┘
```

- Parent forks → child is born
- Child calls `execl()` → child becomes a new program
- Child calls `exit()` → child becomes a zombie
- Parent's `wait()` unblocks → zombie is cleaned up
- Parent continues

**Zombie process — 2 cases:**

1. **Parent dies first:** The `init` process (PID=1) adopts the orphaned child. When the child eventually exits, `init` calls `wait()` to clean it up.
2. **Child dies first, parent never calls `wait()`:** Child stays as zombie, occupying a slot in the process table. If many zombies accumulate, the table fills up — bad!

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: wait() is blocking
> `wait()` is **blocking** — the parent will pause until a child finishes. If you don't want to block, look into non-blocking variants like `waitpid()` with `WNOHANG`.

> [!danger] Pitfall: Zombies are already dead
> Zombies are **NOT killed** — they're already dead. You clean them up by having the parent call `wait()`.

> [!danger] Pitfall: Forgetting wait() causes resource leaks
> Forgetting `wait()` in long-running programs is a **serious resource leak**. It can exhaust the process table.

> [!danger] Pitfall: kill command doesn't work on zombies
> You **cannot kill a zombie** with the `kill` command — the process is already terminated; only `wait()` can clean it up.

---

### ❓ Mock Exam Questions

> [!question] Q1: wait() Return Value
> What does `wait()` return, and what does it write into its parameter?
> <details><summary>Answer</summary>
>
> **Answer:**
> `wait()` returns the **PID of the terminated child**. It writes the child's **exit status** into the `status` pointer parameter (if non-NULL).
> </details>

> [!question] Q2: Zombie Process
> What is a zombie process, and why can't you kill it with the `kill` command?
> <details><summary>Answer</summary>
>
> **Answer:**
> A zombie is a process that has **terminated** but whose entry remains in the process table because the parent hasn't called `wait()` yet. The `kill` command doesn't work because the process is already dead — it's not running, just waiting to be reaped.
> </details>

> [!question] Q3: Orphaned Process
> What happens to an orphaned child process (one whose parent exits first)?
> <details><summary>Answer</summary>
>
> **Answer:**
> The `init` process (PID 1) **adopts** the orphaned child. When the child eventually exits, `init` calls `wait()` to clean it up. This prevents orphans from becoming permanent zombies.
> </details>

> [!question] Q4: Waiting for Multiple Children
> A parent forks 3 children and needs to wait for all 3 to finish before proceeding. Write pseudocode showing how the parent would use `wait()` to correctly collect all 3 children.
> <details><summary>Answer</summary>
>
> **Answer:**
> ```c
> // Fork 3 children
> for (int i = 0; i < 3; i++) {
>     if (fork() == 0) { /* child code */ exit(0); }
> }
> // Wait for all 3 children
> for (int i = 0; i < 3; i++) {
>     wait(NULL);  // Each call reaps one child
> }
> printf("All children done\n");
> ```
> </details>

## 12. Process States in Unix

### 🧠 Core Concept

A Unix process can be in one of 5 states:

| State | Description |
| :--- | :--- |
| **Ready** | Waiting for CPU time — runnable but not currently running |
| **Running** | Currently executing on the CPU |
| **Suspended** | Waiting for a resource (e.g., I/O) — cannot run until it arrives |
| **Stopped** | Paused by a STOP signal (e.g., Ctrl+Z in terminal) |
| **Zombie** | Finished execution, awaiting parent's `wait()` call |

**State transitions:**

```
fork() ──→ [Ready] ⇄ context switch ⇄ [Running]
                                           │
                      ┌────────────────────┤
                      ↓                    ↓
                 [Suspended]          STOP signal → [Stopped]
                      │                    │
               resource ready        CONT signal
                      │                    │
                      └──────→ [Ready] ←──┘
                                           │
                                       exit()
                                           ↓
                                       [Zombie]
```

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: Ready ≠ Running
> A "ready" process wants to run but is waiting for the scheduler to give it CPU time. "Running" means actually executing on the CPU.

> [!danger] Pitfall: Suspended ≠ Stopped
> **Suspended** means waiting for I/O or another resource. **Stopped** means paused by a signal (like Ctrl+Z). They have different causes and different resume mechanisms.

> [!danger] Pitfall: Zombie is a real state
> Zombie is a **real state** in the diagram, not just a colloquial term. It's a legitimate process state that requires explicit cleanup.

> [!danger] Pitfall: One CPU, one Running process
> A process can only be **Running on one CPU core at a time** (in the basic model). With $n$ CPUs, at most $n$ processes can be Running simultaneously.

---

### ❓ Mock Exam Questions

> [!question] Q1: Suspended vs Stopped
> What is the difference between the "Suspended" and "Stopped" states?
> <details><summary>Answer</summary>
>
> **Answer:**
> - **Suspended**: Process is waiting for I/O or a resource (e.g., disk read). It becomes Ready when the resource becomes available.
> - **Stopped**: Process was paused by a signal (e.g., `SIGSTOP`, Ctrl+Z). It becomes Ready when it receives `SIGCONT`.
> </details>

> [!question] Q2: STOP Signal
> What signal causes a Running process to move to the Stopped state?
> <details><summary>Answer</summary>
>
> **Answer:**
> The **`SIGSTOP`** signal (or `SIGTSTP` from Ctrl+Z) causes a Running process to move to the Stopped state. The process is paused until it receives `SIGCONT`.
> </details>

> [!question] Q3: Zombie Cleanup
> Which system call triggers the transition from Zombie to fully cleaned up (removed from process table)?
> <details><summary>Answer</summary>
>
> **Answer:**
> The parent's **`wait()`** (or `waitpid()`) call. It reads the zombie's exit status and removes the process table entry, fully cleaning up the process.
> </details>

> [!question] Q4: State Journey
> Trace the complete state journey of a child process, from the moment `fork()` is called by its parent to the moment it is fully cleaned up. Name every state it passes through and what causes each transition.
> <details><summary>Answer</summary>
>
> **Answer:**
> 1. `fork()` called → **New** (created)
> 2. OS admits process → **Ready** (waiting for CPU)
> 3. Scheduler selects it → **Running** (executing)
> 4. Calls I/O (e.g., `read()`) → **Suspended** (waiting for I/O)
> 5. I/O completes → **Ready** (ready to run again)
> 6. Scheduler selects it → **Running** (resumes)
> 7. Calls `exit()` → **Zombie** (terminated, waiting for `wait()`)
> 8. Parent calls `wait()` → **Removed** (fully cleaned up)
> </details>

## 13. Implementing `fork()` & Copy-on-Write

### 🧠 Core Concept

**How `fork()` works internally (simplified steps):**

1. Create a new address space for the child
2. Allocate a new PID `p'`
3. Create kernel data structures (e.g., process table entry)
4. Copy kernel environment from parent (e.g., scheduling priority)
5. Set child's context: `PID = p'`, `PPID = parent's PID`, CPU time = 0
6. **Copy memory regions** from parent (program code, data, stack) ← expensive!
7. Acquire shared resources (open file descriptors, working directory)
8. Copy hardware context (registers, program counter) from parent
9. Add child to the scheduler's ready queue

**The memory copy problem:**

Step 6 is very expensive — potentially copying gigabytes of memory. But most of it may never be used! This is where **Copy-on-Write (CoW)** helps:

| Situation | Action |
| :--- | :--- |
| Page is only read | Share the page (read-only) |
| A write is attempted | Duplicate the page |

- Parent and child initially **share** the same physical memory pages
- Both pages are marked **read-only**
- When either process tries to **write**, the OS makes a private copy of just that page
- This way, you only copy what's actually needed — much more efficient!

> [!tip] Memory Management
> Memory is managed at the **page** level (a contiguous block of memory locations), not byte by byte.

**Modern Linux: `clone()`**

`fork()` is a full duplication. Linux's `clone()` is a more flexible version that lets you control *exactly* what is shared between parent and child (memory, file descriptors, signal handlers, etc.). It is the foundation for threads in Linux.

---

### ⚠️ Common Pitfalls

> [!danger] Pitfall: CoW is transparent
> Copy-on-Write is an optimization — the **behaviour of `fork()` is unchanged**. From the programmer's view, child data is still an independent copy.

> [!danger] Pitfall: Copy happens on write, not on fork
> The "copy" doesn't happen immediately with CoW — only when a write occurs. At `fork()` time, parent and child share the same physical pages.

> [!danger] Pitfall: clone() ≠ fork()
> `clone()` gives you fine-grained control; `fork()` is always a full duplicate (modulo CoW). They serve different purposes.

> [!danger] Pitfall: CoW still has overhead
> Even with CoW, creating many child processes still has overhead (kernel structures, page table entries, etc.). Use wisely.

---

### ❓ Mock Exam Questions

> [!question] Q1: Most Expensive Step
> In the simplified `fork()` implementation, which step is the most expensive, and why?
> <details><summary>Answer</summary>
>
> **Answer:**
> **Step 6 — copying memory regions**. This can involve copying gigabytes of data from parent to child. Even with CoW, page table entries must still be duplicated.
> </details>

> [!question] Q2: Copy-on-Write Explanation
> Explain the Copy-on-Write optimization in one or two sentences.
> <details><summary>Answer</summary>
>
> **Answer:**
> CoW defers memory copying until a write is needed. Parent and child share the same physical pages (marked read-only); when either process writes, the OS copies just that page.
> </details>

> [!question] Q3: clone() vs fork()
> What is the key limitation of `fork()` that motivated the creation of `clone()` in Linux?
> <details><summary>Answer</summary>
>
> **Answer:**
> `fork()` always creates a **full copy** of the parent (modulo CoW). `clone()` allows fine-grained control over what is shared vs. copied (memory, file descriptors, signal handlers). This is essential for implementing threads, where sharing is desired.
> </details>

> [!question] Q4: Memory Calculation
> A parent process has 1GB of data in memory and calls `fork()`. Without Copy-on-Write, how much memory would be needed? With Copy-on-Write, if the child only reads 10MB and writes 5MB of data, approximately how much extra memory is actually duplicated?
> <details><summary>Answer</summary>
>
> **Answer:**
> - **Without CoW:** 2GB total (1GB parent + 1GB child copy)
> - **With CoW:** Only the **5MB of written pages** are duplicated. The 10MB read is still shared. Total ≈ 1GB + 5MB extra.
> </details>

## Question 1: Process Creation Recap

### 🧠 Core Concept

`fork()` creates a child process. The parent gets the child's PID as the return value; the child gets `0`. `wait()` blocks the calling process until **any** child exits.

---

### Case Analysis
```C
int main( ) {
    //This is process P 
    if ( fork() == 0 ){   
        //This is process Q   
        if ( fork() == 0 ) { 
            //This is process R           
	        ......  
            return 0;   
        }  
        <Point α>
    }
	<Point β>
    return 0;
}
```

#### Case 1: Point α = _nothing_, Point β = `wait(NULL)`

**Claim:** 
1. Q always terminates before P. ✅
2. R can terminate any time. ❌

**Why?**
- Only P (at Point β) calls `wait()`, so P waits for Q to exit.
- Q has **no** `wait()` at Point α, so Q does NOT wait for R.
- Therefore Q can exit before R finishes — **Q still terminates before P** ✅
- But the claim also says "R can terminate any time w.r.t. P and Q" — this part fails because Q wait for R at Point β after Q exits from the if block. 
---

#### Case 2: Point α = `wait(NULL)`, Point β = _nothing_

**Claim:** 
1. Q always terminates before P. ❌
2. R can terminate any time. ✅

**Why?**
- Q calls `wait(NULL)` at Point α → Q **waits for R** to exit first.
- P has **no** `wait()` at Point β → P does **not** wait for Q.
- So the ordering is: R exits → Q exits, but P can exit at any time independently.
- The claim "Q always terminates before P" is **FALSE** because P does not wait for Q.

---

#### Case 3: Point α = `execl(valid executable...)`, Point β = `wait(NULL)`

**Claim:** 
1. Q always terminates before P. ✅
2. R can terminate any time. ✅

**Why?**
- `execl()` **replaces** Q's memory image with a new executable — but crucially, the **PID stays the same**.
- P called `fork()` so P still has Q as its child. When P calls `wait(NULL)`, it waits for that child PID to finish — regardless of the fact that Q has now exec'd into something new.
- P will always outlive Q. ✅
- R was spawned before `execl()`, so R is an orphan or child of Q-turned-new-process. Its timing relative to P and Q is unconstrained. ✅

> 💡 **Key insight:** `execl()` changes the _program_ but NOT the process identity. The parent-child relationship is preserved!

---

#### Case 4: Point α = `wait(NULL)`, Point β = `wait(NULL)`

**Claim:** P **never terminates**. ❌

**Why?**
- Q calls `wait(NULL)` at Point α. But at that point, **Q's only child is R**. So Q waits for R, then Q exits. ✅
- P calls `wait(NULL)` at Point β. P's only child is Q. Once Q exits, P's `wait()` returns and P exits too. ✅
- The critical note: **`wait()` does not block when a process has no children.** So no deadlock occurs.

> 💡 **Pro-Tip:** A common mistake is assuming `wait()` blocks forever. It only blocks if there ARE children to wait for. If a process has no children, `wait()` returns immediately with -1.

## Question 2: Behaviour of `fork()` 🔬

### The Code Setup
```C
int dataX = 100;             

int main() {
    pid_t childPID;
    int dataY = 200;            
    int* dataZptr = (int*) malloc(sizeof(int));
    *dataZptr = 300;

    //First Phase

    printf("PID[%d] | X = %d | Y = %d | Z = %d |\n",
            getpid(),  dataX, dataY, *dataZptr);

    //Second Phase

    childPID = fork();
    printf("*PID[%d] | X = %d | Y = %d | Z = %d |\n",
            getpid(),  dataX, dataY, *dataZptr);
            
    dataX += 1;
    dataY += 2;
    (*dataZptr) += 3;
    
    printf("#PID[%d] | X = %d | Y = %d | Z = %d |\n",
            getpid(),  dataX, dataY, *dataZptr);

    //Insertion Point

    //Third Phase

    childPID = fork();

    printf("**PID[%d] | X = %d | Y = %d | Z = %d |\n",
            getpid(),  dataX, dataY, *dataZptr);

    dataX += 1;
    dataY += 2;
    (*dataZptr) += 3;

    printf("##PID[%d] | X = %d | Y = %d | Z = %d |\n",
            getpid(),  dataX, dataY, *dataZptr);

    return 0;
```
Three variables, three memory segments:

- `dataX` → **Data segment** (global variable, initialized)
- `dataY` → **Stack segment** (local variable inside `main()`)
- `*dataZptr` → **Heap segment** (dynamically allocated via `malloc()`)

> Note: `dataZptr` itself (the pointer variable) lives on the **stack**, but the memory it _points to_ lives on the **heap**.

---

### Part (a) — Memory Regions

|Variable|Segment|Why|
|---|---|---|
|`dataX`|Data|Global, statically allocated|
|`dataY`|Stack|Local variable in `main()`|
|`*dataZptr`|Heap|Allocated with `malloc()`|

---

### Part (b) — What `fork()` does to memory

When `fork()` is called:

- The child gets a **complete copy** of the parent's memory (copy-on-write).
- The `*` messages (printed right after `fork()`) show **identical values** in parent and child — the copy is exact.
- The `#` messages (after modifications) show **different values** — proving that each process has **independent memory**.

> [!tip] Note
> This is the fundamental property: after `fork()`, parent and child are isolated. Changes in one do not affect the other.

---

### Part (c) — Process Tree

Starting with PID 2000:

```
First Phase: Only 2000 runs
         [2000]

Second Phase: fork() → creates 2001
         [2000]
            └── [2001]

Third Phase: both 2000 AND 2001 call fork()
         [2000]          [2001]
            └── [2002]      └── [2003]
```

All four processes (2000, 2001, 2002, 2003) are alive and running in the third phase. Each child inherits the **modified**values from its parent at the time of the fork.

---

### Part (d) — Can output ordering differ?

**Yes!** 🎲

Once processes are created, the OS **scheduler** decides who runs next. The scheduler is non-deterministic from the program's perspective. Different runs can produce different output orderings.

---

### Part (e) — What pairs can NEVER swap?

These orderings are **always guaranteed**:

1. Within a single process, sequential order is always preserved: `*` always before `#`, and both always before `**` and `##`.
2. The First Phase message (from 2000 alone) always comes **first** — only one process exists at that point.
3. `*` and `#` from the same process always appear before that process's `**` and `##`.

**Common wrong answers:**

- ❌ "Child always prints before parent" — wrong, they're scheduled independently.
- ❌ "All messages from Phase N before Phase N+1" — wrong, the parent could sprint ahead through all phases before any child runs.

---

### Part (f) — Effect of inserting `sleep(5)` for child after Second Phase

```c
if (childPID == 0) {
    sleep(5);
}
```

This pauses process **2001** (the child of the second fork) for 5 seconds. Likely outcome:

- 2000 and 2002 will complete their Third Phase messages well before 2001 wakes up.
- 2001 and 2003 will print their Third Phase messages after the 5-second delay.

> [!warning] Warning
> This is still not 100% deterministic! The sleep creates a _likely_ ordering, not a guaranteed one. Other system load can affect timing.

---

### Part (g) — Effect of inserting `wait(NULL)` for parent after Second Phase

```c
if (childPID != 0) {
    wait(NULL);
}
```

This makes process **2000** (the parent) wait for **2001** to finish before moving on to the Third Phase. Step-by-step:

1. 2000 prints `*` and `#`, then hits `wait()` — it **pauses**.
2. 2001 moves ahead, spawns 2003, prints `**` and `##`, then exits.
3. 2000's `wait()` returns → 2000 spawns 2002.
4. 2000 and 2002 print their `**` and `##` messages independently.
5. 2003 continues independently throughout all of this.

> 💡 **Key insight:** `wait()` is a **synchronization primitive**. It lets you enforce ordering between parent and child.

## Question 3: Parallel Computation with Multiple Processes ⚡

### Core Concept
Use `fork()` + `execl()` to spawn multiple child processes that run in **true parallel**, each computing prime factors of a different number.

### The Mechanism

```
Parent reads N numbers
  └─ for each number:
       fork() → child
       child: execl("./PF", number) → runs PrimeFactors
       parent: loops to next number (doesn't wait yet)
  └─ after all forks:
       wait() in a loop → collect results as they finish
```

Using `wait()` (waits for **any** child) means results are printed **as soon as they're ready** — fast computations (small/composite numbers) finish first.

### `wait()` vs `waitpid()`

||`wait()`|`waitpid(pid, ...)`|
|---|---|---|
|Waits for|Any child|Specific child PID|
|Result order|Ready-first (fastest wins)|Creation order (fixed)|
|Use case|Parallel, report ASAP|Ordered results needed|

> 💡 **Pro-Tip:** Using `waitpid()` forces the parent to wait for children in creation order, so even if child 3 finishes before child 1, the parent won't acknowledge child 3 until child 1 is done. This kills the parallelism benefit for reporting!

### The Cost-Benefit Reality

- **Benefit:** True parallel execution on multi-core systems → faster total time.
- **Cost:** `fork()` + `execl()` has overhead (memory copy, OS bookkeeping).
- If only 1 CPU core, or overhead > time saved, you see **no improvement** (or even slowdown).

## Additional Question 4: `fork()` Inside Recursion 🌀

### The Code

```c
int factorial(int n) {
    if (n == 0) {
        fork();   // fork happens here!
        return 1;
    }
    return factorial(n-1) * n;
}
```

### Why does `fac(2) = 2` print twice?

When `fork()` is called inside `factorial(0)`, **both** parent and child have identical stack frames:

- Both are inside `factorial(0)` about to `return 1`
- Both will unwind through `factorial(1)` → `factorial(2)` → `main()`
- Both will reach `printf("fac(2) = %d\n", ...)`

> 💡 **Key insight:** `fork()` duplicates the **entire process**, including the **call stack**. The child doesn't restart from `main()` — it continues from exactly where the fork happened.

**Output:**

```
fac(2) = 2
fac(2) = 2
```

## Additional Question 5: Fork with x and y 🔢

### Setup

```
Process 100: x=10, y=123 (initial)
y = fork();   → creates 101, y=101 in parent, y=0 in child(101)
if (y==0) x--; → only 101 does x-- → x=9 in 101
y = fork();   → 100 creates 102, 101 creates 103
```

### Values table

|PID|x at print|y at print|
|---|---|---|
|100|10 (never decremented)|102 (child of 2nd fork)|
|101|9 (decremented once)|103 (child of 2nd fork)|
|102|9 (inherited x=10, then y==0 so x--)|0|
|103|8 (inherited x=9, then y==0 so x--)|0|

### A valid output:

```
[PID 100]: x=10, y=102
[PID 102]: x=9, y=0
[PID 101]: x=9, y=103
[PID 103]: x=8, y=0
```

### A subtly wrong output:

```
[PID 100]: x=10, y=102
[PID 101]: x=9, y=0    ← WRONG: 101's y should be 103 (PID of its child), not 0
[PID 102]: x=9, y=103  ← WRONG: 102's y should be 0 (it's a child), not 103
[PID 103]: x=8, y=0
```

The mistake: PIDs 101 and 102 have their `y` values swapped. 101 is the **parent** at the second fork (gets child PID 103), and 102 is the **child** (gets y=0).

## Additional Question 6: `wait()` vs `waitpid()` with 3 children 👨‍👩‍👧‍👦

### Setup

Parent (PID 100) forks 3 children: 101, 102, 103. Each does some work and exits.

### Using `wait(NULL)` in a loop:

```c
for (i = 0; i < 3; i++) {
    wait(NULL);
    printf("Parent: one child exited\n");
}
```

- Waits for **any** child to exit.
- Order of "Child X is done!" messages is non-deterministic.
- But each "Parent: one child exited" only prints **after** some child has actually exited.
- All 3 children finish before "Parent [100] is done!" prints.

### Using `waitpid()` in a loop:

```c
for (i = 0; i < 3; i++) {
    waitpid(cPidArray[i], NULL, 0);
    printf("Parent: one child exited\n");
}
```

- Waits for children in **creation order**: 101, then 102, then 103.
- Even if 103 finishes first, the parent won't acknowledge it until 101 and 102 are done.
- This enforces a **strict ordering** of acknowledgment.

### Guaranteed in both cases:

- A "Child X is done!" message always precedes the corresponding "Parent: one child exited".
- All 3 children finish before "Parent is done!" prints.

> 💡 **Pro-Tip for exams:** The key distinction is "waits for **any** child" (`wait`) vs "waits for a **specific** child" (`waitpid`). This determines whether results are reported in completion order or creation order.
